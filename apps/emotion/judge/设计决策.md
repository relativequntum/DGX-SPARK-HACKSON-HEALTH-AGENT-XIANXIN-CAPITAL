## 借鉴什么，不借鉴什么

**Jev 是什么**：TypeSafe 的云端「决策」模型（OpenRouter 上叫 `typesafe/jev-1.13`，直连叫 `jev-latest`）。它不生成文本，只对一组固定题目作答：`noul` 题给一个布尔概率，`choice` 题给各选项概率，`score` 题给 0–9 档。输入 `state` 是任意 dict，题目带英文 `instructions` 和 `criteria`。

**微信版的用法**：对方每来一条消息 → Jev 答 7 道判断题（字面/意图/紧张度/该不该说实质内容/最佳动作/对方需要/张力是否已解）→ 把判断折成中文小抄喂给起草模型写 3 条候选 → Jev 再排序。

**我们借什么**：「固定题目 + 类型化答案 + 概率 + 任意 state」这套结构，以及「判断先于生成」的三段式思路。

**我们不借什么**：微信版的题目本身（恋人/朋友语境的意图分类），以及「情绪标签 + 百分比」的呈现方式（决策记录第 11 条明确不做 A 类）。

## 已定

1. **路径**：本地为主、Jev 云端可选。本地用 Spark（或开发期本机 Ollama）上的大模型答题；Jev 云端只作为显式开关。
2. **分两步走**：
   - 预赛（2026-09-29 截止）= **对话重点抓取**：把整段预问诊对话里医生该重点看的句子找出来、分类、排序。
   - 决赛（2026-10-15）= MSE 观察题 + 移植微信 7 题：预诊单沟通状态条目、给阶段一提问 Agent 的措辞小抄。后者要阶段一开接口，届时另发 [裁决]。
3. **预赛输出去向**：医生端「重点定位」视图。问题树选分支、候选提问排序这两项属于阶段一核心逻辑，只在 Issue 里提想法，不做。
4. **「重要」有两把尺子 → 两组题**：
   - 情绪/沟通组：患者在哪几句明显紧张、回避、前后矛盾、有潜台词、发出求助信号。
   - 医疗信息组：主诉、症状变化、用药、过敏、既往史、疑似风险线索。
   - 医疗组与阶段一路线图里的「医生结构化摘要」重叠，在 [任务] Issue 里 @relativequntum 会签，不单开 [会签] Issue。
5. **题目口径**：不出「悲伤/愤怒」这类情绪标签。题目问的是可观察的对话行为（回答充分度、连贯性、紧张度 0–9、字面还是有潜台词、此刻需要什么）。概率只作为置信度显示，每题含 `unknown` 选项。
6. **粒度与时机**：预赛在**会话结束后对整段对话跑一次**。实现上逐个问答对判断、带最近 N 轮上下文、结果挂到「当时在答哪一题」上（对应决策记录第 21 条），最后总排序。实时判断留给决赛「判断结果影响下一问」的场景。
7. **输入**：预赛只用对话文字。`state` 预留 `channels` 字段，决赛把语音/面部观察条目（如「语速变慢、目光移开」）作为文字条目塞进去让判断题一起看。
8. **概率来源**：约束 JSON（Ollama `format` 参数）+ 模型自报各选项分布 + `unknown`。后端接口抽象成一层，Spark 上换 vLLM 后同一接口改读 logprobs。
9. **云端开关语义**：配置 `judge.cloud=true` 且环境变量 `JEV_API_KEY` 存在才调 Jev；只发最近 N 轮文字，不带任何身份信息；每条结果带 `source=local|jev-cloud`；云端失败自动退回本地。符合安全文档「显式开启、告知、最小化、可关」四条。
10. **红旗边界**：医疗组含「疑似风险线索」类别，**只能抬不能压**，永远排在清单最前；代码里不做任何「未命中即安全」的推论；README 与界面注明确定性红旗规则另有其层，本模块不替代。
11. **交付形态**：仓库代码 + 可跑演示（录屏或现场）。医生视图为一页静态 HTML：左侧问答全文、命中的患者回答按类别着色；右侧按重要度排序的清单，每条写类别、置信度、来源，点击跳到原句；顶部固定「待医务人员确认」。不上前端框架。
12. **题目与样本**：Claude 起草两组题（每组 4–6 题，中文选项标签 + 英文 instructions/criteria，照 Jev 格式放独立文件），用户过目后发博士审，博士改了直接替换文件。演示样本为 3–5 段虚构对话，带「应命中哪几句」的金标准标注。
13. **真实录音**：曾有一段来源不确定的问诊录音，按真实数据处理：只在开发者本机用作对照，录音与转写稿从不入库、不上传、不进 Jev 云端，仓库中也不记录其文件名或存放路径。转写用本机的 SenseVoice，医生/患者轮次需另切。
14. **落位**：`apps/emotion/judge/`，输出 JSON 带 `schema_version`，不动 `packages/core`。开一个 [任务] Issue 挂 M3，分支 `feat/issue-<N>-judge`。
15. **Jev key**：用户目前没有（环境里只有 DeepSeek 与 LLM_API_KEY）。本地路径跑通后再去 openrouter.ai 申请，用来对比本地与 Jev 的判断质量并验证退回逻辑。

## 2026-09-24 追加（实现中定下的细节）

16. **本机传输走 Ollama 原生 `/api/chat`，不走 `/v1`**：实测 Ollama 0.34.2 的 OpenAI 兼容端点不认 `think:false`，
    qwen3-vl:8b 照样推理、默认 4096 上下文被吃光、正文为空；原生端点 `think:false` + `format=schema` + `num_ctx 8192`
    后 1.6 秒出完整 JSON。Ollama 关思考后把 qwen3-vl 的正文放进 `message.thinking`，后端取「content 为空就用 thinking」。
    Spark 上的 llama-server 走 `--backend openai`（OpenAI 兼容），两条传输共用 prompt / schema / 答案转换。
17. **模型选型（本机）**：qwen3-vl:8b（1.6–2 秒/次，判断合理）；gemma4:e2b 慢 20 倍且 contains_key_info 判错，不用。
18. **重要度公式**：情绪组 = P(worth_flagging)；医疗组 = P(contains_key_info) × (0.4 + 0.6 × urgency/9)；阈值 0.5。
    风险 = risk_clue ≥ 0.5 或 info_category = risk_clue 或 urgency ≥ 8 或 tension_level ≥ 9，不看 unknown，只抬不压。
19. **unknown 口径**：noul 概率与 0.5 差距 < 0.15；choice 选 unknown 或置信度 < 0.6；score 置信度 < 0.6。
20. **每次调用带 evidence**：让模型引用最能支持判断的原话，医生视图显示为「依据」，方便一眼核对。
21. **评测口径**：命中 = (轮次, 题组)；gold 分 expected / allowed（模糊项命中不算错）；风险单独算召回。

## 2026-09-29 追加（#12，PR #4 评审跟进）

25. **watch 单条会话出错不带崩进程**：每条会话单独 try，出错记入 failures 按 `--retry` 退避，日志只写会话编号前 8 位和异常类名；
    主循环也兜一层。读问诊记录与 `_scan` 同一口径 `errors="replace"`，写了半行不再抛 UnicodeDecodeError。
26. **部分失败不算完**：`0 < errors < 判断次数` 时照常写出结果给医生看，同时记入 failures，`--retry` 秒后整段重判，全部成功才清掉。
    failures 只在内存里，所以「判全了没有」以磁盘上的 `judge.json` 为准：`errors > 0` 或解析不了（写了一半）都算没判全，
    服务重启后马上重判一次，之后照样按 failures 退避，不空转。代价是每轮扫描要读一遍已有结果文件。
27. **risk_clue 答 true 就算风险**：本地模型的 noul 题是「布尔 + 自报置信度」，`answer=true, confidence=0.4` 原本换算成 0.4，
    被第 18 条的 ≥ 0.5 压掉。改在答案转换处（`backends/prompt.py`，唯一还看得到布尔值的地方）给 risk_clue 兜底到 0.5：
    判为风险、置顶，标签显示「疑似风险线索（请人工核实）（不确定）」；`judge.json` 字段不变，其他题和 Jev 云端不受影响。
